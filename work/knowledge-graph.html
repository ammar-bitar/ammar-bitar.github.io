A knowledge graph for scientific peer review

How I turned manuscripts into a graph of hypotheses, methods, results and claims, so that reviewer agents can verify what a paper says against what it shows.

Where
BIIE, Zürich, 2025 to now
Scope
Ontology, ingestion, entity resolution, store, query and traversal layer, subgraph reconstruction
Sits inside
The multi-agent peer-review system it was built for, in production use by scientists across the institute
Design
Symbolic end to end, so every node, edge and retrieval path stays readable and a review can point at the exact result a claim rests on
About the figures
The diagrams and interactive pieces here are built for this page: working simulations of the ideas, written from scratch so you can play with them.

01Why a graph

A reviewer agent that only retrieves text chunks can summarise a paper. It cannot reliably tell you whether the paper's main claim is supported by its own results, whether a method section matches the experiment behind Figure 3, or whether a result on page 12 contradicts a hypothesis on page 2. Those are the questions reviewers spend most of their time on, and answering them needs the structure of the paper, not just its text.

So the system first breaks each manuscript into components and the typed relations between them. Retrieval then means following those relations: start at a claim, go to the results it rests on, then to the experiments that produced them, and give the agent a self-contained bundle of evidence with its sources attached.

02The ontology

The ontology is custom, aligned in part with ISA and MeSH where existing vocabularies fit. It breaks a manuscript into component types including hypotheses, assumptions, methods, experiments, observations, results, data and claims. Relations are typed. The two the reviewer agents lean on most are supports and contradicts, which run between results and the hypotheses or claims they bear on.

Why symbolic. Embeddings would have been quicker to set up, and they still return the passage a sentence came from. What they don't give you is how two parts of a paper relate: that a claim rests on the result in Table 2, that the experiment behind it used the method on page 4, or that a later observation contradicts it. Reviewers reason about exactly those relations, so the graph models them explicitly and the agents follow them.

03The pipeline

The pipeline runs from source documents to evidence bundles in six steps.

  • Ingestion takes manuscripts and supporting material from heterogeneous sources and normalises them before decomposition.
  • Decomposition maps each document onto the ontology's component types and proposes the relations between them.
  • Entity resolution decides when two mentions refer to the same thing, such as one dataset cited two ways or one method under two names. It combines identifier-based matching where identifiers exist, string matching where they do not, and LLM-assisted matching for the rest. Most of the difficult cases end up here.
  • The store is custom, built around the traversals the agents run and the source information each node carries.
  • Traversal performs multi-hop retrieval for provenance and traceability: from any component, out along typed relations, with the path kept.
  • Subgraph reconstruction turns a traversal into a self-contained bundle with what an agent needs to judge one claim, each element traceable to its source passage.

04How the agents use it

The agents use the graph in four main ways:

  • Claim verification. Start at a claim, walk to the results it rests on, and check whether those results actually support it.
  • Contradiction finding. Follow contradicts edges to find results that go against the paper's own hypotheses.
  • Provenance. Every statement in a review can be traced back through the graph to the passage it came from, so a scientist reading the review can check it.
  • Novelty checks. Compare a manuscript's components against what is already in the graph from other work.

The graph is one input among several. The agents also work through our MCP tools for literature retrieval, structured biological-data access and figure and table analysis, which the team built together and which I customised for the review pipeline.

Validation. The whole system was evaluated together. I built the evaluation framework, with rubric-based LLM-as-judge scoring, critique matching against human reference reviews and inter-rater reliability, and ran a blinded, pre-registered validation study on 30 preprints with a panel of 16 PhD domain experts. The system is in production use by scientists across the institute, and a paper on the architecture, evaluation framework and human validation is in preparation.
